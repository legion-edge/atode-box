# 詳細画面（Phase 1 / Issue #9）

確認日: 2026-10-03〜04 JST。

通知一覧の項目を開くと、カテゴリ、任意のタイトル、原文、保存日時、次回通知日時、通知コンテキストを表示する。完了済みは次回通知なしと示す。詳細画面は確認・必要な編集のための画面で、登録時の分類や日時選択を増やさない。

http/httpsでホストのあるURLだけに「開く」を表示し、`url_launcher` の `LaunchMode.externalApplication` を使用する。旧データのURLフィールドがnullなら原文の最初のhttp/https URLを候補にする。編集で空欄にすると空文字を保存して明示的なURL除去を表し、原文から再抽出しない。URLを開いても状態・通知予定・原文は変えない。外部アプリが開けない場合や例外は画面で伝える。

編集できるのはタイトル・URL・カテゴリ。原文、保存日時、item ID、通知IDを維持する。保存はrepositoryの直列処理内で最新recordに対して行い、編集中の通知による完了やあとで回数を古い画面のsnapshotで上書きしない。activeのカテゴリ変更では現在のあとで段階を保って予定を再計算する。次回未設定のactiveも予定を計算する。タイトル・URLだけの変更は設定済み予定を動かさない。completedを編集してもactiveに戻さず、次回予定・コンテキストをクリアする。deletedの編集は拒否する。

通知同期ではプラグインに保存された予約のpayload・タイトル・本文を照合する。同じUTC予定時刻でもカテゴリ変更で文面が異なれば取消・再予約し、取消が失敗しても次回の通常同期で再試行する。古い通知の完了・あとでは、repositoryの単一の直列処理内で最新recordのactiveと予定UTC一致を再確認してから反映する。予定変更・削除が割り込んだ通知操作は無視し、同時刻のメタデータ編集は最新タイトル・URLを維持する。この直列化は同一repositoryインスタンス内の処理で、将来の背景isolate対応を実装したものではない。

削除は確認ダイアログを経てdeleted状態を保存し、次回予定とコンテキストをクリアして通知同期を行う。物理削除・原文消去・復元UIは今回の範囲外。保存に失敗したら画面に残り、編集内容を保って再試行できる。保存成功後にOS通知更新が失敗した場合は、保存を取り消さず次回起動・復帰で再試行する旨を表示する。

Galaxy A25 5Gの別application IDの専用アプリで、本人が一覧→詳細・外部URL遷移・タイトル／URL／カテゴリ編集・URL除去・削除確認の取消と削除・URLなし・未保存編集の破棄を確認した。保存状態は読み取り照合し、タイトル編集後のbaseline以降のID・原文・保存日時の保持、カテゴリ変更の再計算、soft deleteを確認した。初回編集前のID・保存日時のbaselineは未取得で、その最初の前後一致は直接証明できない。画面とブラウザの観察は本人報告であり、widgetの注入URL関数やfake通知ポートと区別する。

専用アプリは通知未許可のままで、許可状態のOS予約更新・実配送は実機未検証。iPhone実機も未実施。最終状態はdeleted2件・表示対象0件・専用OS予約0件で、物理削除ではない。既存Galaxyアプリの保存文書と10月4日21:00の予約を保持した。詳細は[検証記録](VALIDATION.md)を参照。
