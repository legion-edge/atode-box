# 固定高さの入力枠（実機試験候補）

本人の「一旦、固定でやってみようか」に基づく候補。診断版で採取した187件では、入力枠が残り高さに合わせて伸縮し、最小180pxに達すると止まる設計と寸法が一致した。重いlayout処理や追加120ms遅延を原因とする根拠は得られず、体感の原因は未確定。入力枠の大きな伸縮を取り除く案を試す。

## 高さと例外

高さ（logical pixel）は `clamp(view高さ × 0.24, 144, 180) × max(1, textScaler.scale(1))`。IME insetから独立したview寸法を使い、同じ画面寸法・文字倍率の開閉では不変。回転、画面分割等のview寸法変更、文字倍率変更時には再計算する。

| Widget試験条件 | 実測入力枠高さ |
| --- | ---: |
| Galaxy相当384×853.33、通常文字 | 180px |
| 320×640、文字倍率2 | 307.2px |
| 240×480、文字倍率2 | 288px |
| 640×320、通常文字 | 144px |
| 360×800、文字倍率3 | 540px |

通常の縦画面は従来の最小180pxを維持し、低い横画面は144pxを基準とする。大文字は読みやすい行領域を保つため高さを比例拡大し、上限で文字倍率を切り捨てない。実機で候補の180pxを確認した結果ではなく、自動Widget試験での寸法。

## 挙動と確認

Expanded、IntrinsicHeight、残り高さを埋めるConstrainedBoxを除き、一定高さのTextFieldとページ全体のSingleChildScrollViewにする。長文は入力欄内部をスクロールする。小画面・大文字では枠が表示領域より高くなり、ページスクロールで末尾caretや登録・貼り付けへ到達する。閉じたとき一度に見える入力量が減り、画面下に余白が出る場合がある。

同じcontroller・focus・selectionを保持し、既存caret可視化のguardとpost-frame処理を残す。Androidのinset即時反映、iOSの120ms補間、動きを減らす設定、PR38の位置が動かないfilterを維持する。5条件の連続IME変化で固定高さ、長文の内部scroll、末尾caret位置、ボタンのhit testと到達を確認する。既存の回転・長文保存・安全領域試験も実行する。

診断buffer・VM extension・RenderObject計測はこの候補に含めない。端末更新・本人操作は親の案内後。元アプリ4件・本日21時JST予約と詳細試験の保存データ・権限を保全し、mergeは行わない。
