# 通知予定ルール（Phase 1 / Issue #6）

確認日: 2026-09-29。

## 入出力と時刻

`ScheduleEngine` は保存済みカテゴリ、任意の `content_length`、生活時間設定、注入した現在時刻、タイムゾーンから、UTCの次回時刻・context・根拠を返す。同じ入力は同じ結果になる。呼び出し元は `DateTime.now()` を操作の開始時に一度だけ取得して渡す。保存時刻と通知計算に同じ時刻を使う。

通常の `DeviceZone` は端末の現在のローカルタイムゾーンを使う。固定オフセットを渡すと端末環境に依存しないテストができる。現地時刻は端末のタイムゾーン規則でUTCへ変換し、存在しない夏時間の時刻はDart/OSの変換結果に従う。端末タイムゾーンが後で変わった場合、保存済みUTC予定は自動で移動しない。通知登録を担う後続Issueでタイムゾーン変更時に再計算する。

候補は常に注入時刻より後にする。ちょうど同時刻の候補も次の対象日に進む。予定の重複はこの段階では許す。通知の間引きは行わない。

## 初回予定

| カテゴリ | 初回context | 現地時刻 |
| --- | --- | --- |
| 読む（短い・不明） | 帰宅開始/中 | 設定した帰宅開始時刻。休日を除く |
| 読む（長い） | 休日昼 | 12:00 |
| 見る（短い・不明） | 夜 | 21:00 |
| 見る（長い） | 休日夜 | 20:00 |
| 行く | 休日の前日夜 | 21:00。連休初日の前日 |
| 買う | 休日昼 | 12:00 |
| やる | 帰宅後 | 設定した帰宅後時刻。休日を除く |
| アイデア | 1週間後 | 7暦日後の21:00 |
| メモ | 翌日夜 | 翌暦日以降の21:00 |

`content_length` は `unspecified` / `short` / `long` の明示属性として保存する。不明な「読む」「見る」は短いルールを使う。文字数、URLのパス、リンク本文から長さを推定しない。1週間後・翌日夜は端末の暦日で数え、24時間の固定加算ではない。

## 休日

土日と日本の祝日・休日は設定で独立して有効化する。休日が連続するとき、前日夜は連休開始前の非休日を選ぶ。両方を無効にした場合、休日contextは1週間後へ置き換える。

内閣府「[国民の祝日について](https://www8.cao.go.jp/chosei/shukujitsu/gaiyou.html)」（2026-09-29確認）が公表する2026年・2027年の日付を同梱した。振替休日（2026-05-06、2027-03-22）と祝日に挟まれた休日（2026-09-22）も含む。春分・秋分の日は年ごとの公表日をそのまま使用する。2028年分は同ページによると2027年2月公表予定のため、現時点で推測しない。日本の祝日判定が必要な未収録年は明示的に失敗する。次の公式公表後にデータを更新し、テストする。週末判定だけで祝日を代用しない。

追加パッケージは使用しない。年次データをアプリ内に保ち、外部通信と依存の保守負担を避ける。

## 「あとで」と設定変更

「あとで」はactiveの項目のみ受け付ける。1回目は翌日夜、2回目は休日昼（「見る」は休日夜）、3回目以降は操作日から1週間後の夜へ進める。`LocalRepository.snoozeItem` が `snooze_count`、context、`next_notify_at` を単一の永続書き込みで更新する。保存失敗時は回数も時刻も進まない。OS通知の更新は後続Issueで行う。

設定画面は `saveSettingsWithSchedules` を使う。`SettingsChange.scheduleChanged` が真なら、保存済みactive項目を現在時刻と新設定から再計算し、設定と全予定を単一の永続書き込みにまとめる。再計算は現在のsnooze段階を維持する。completed/deletedは変更しない。初回案内完了フラグだけの変更では予定を触らない。既存の `saveSettings` は設定だけを保存する低水準APIとして残し、生活時間・休日の変更には使わない。OS通知の再登録は後続Issueの境界。

このIssueでは通知の表示・配信、AIによる自由な日時生成、スマート学習を実装しない。
