# アーキテクチャ

更新日: 2026-09-27。現段階は設計とFlutter雛形であり、下記の機能境界は後続Issueで実装する。

## Phase 1の構成

Flutterアプリ1つでiOS / Androidを対象にする。画面（入力、通知一覧、詳細、設定）からユースケース（登録、分類、次回通知決定、完了、あとで）を呼び、ドメインの型とルールをプラットフォームAPIから分離する。永続化とOS通知は抽象インターフェースを介して接続する。状態管理・DB・通知プラグインは各Issueで必要条件を確認して選ぶ。

```text
画面 → アプリ操作 → 分類・通知ルール → 保存ポート → 端末内ストレージ
                         └────────────→ 通知ポート → iOS / Android通知
```

登録は入力をローカルへ先に保存し、成功をすぐに返す。分類と通知準備が失敗しても入力を失わない設計とし、再処理可能な状態を持たせる。具体的なキュー／トランザクションの実装は保存Issueで決める。クリップボードは「貼り付けて追加」を押した時だけ読む。共有シートはPhase 2で追加する。

## 分類とスケジュール

Phase 1はルールベースで7カテゴリへ分類し、判定しきれないものは「メモ」とする。推定読了／視聴時間、準備量、価格感などが不明なら保守的な既定値を使う。日時決定はカテゴリ、通知コンテキスト、生活時間設定、休日判定、あとで回数を入力とする決定的な関数に置く。タイムゾーン、休日の前日、日本の祝日、過去時刻回避、設定変更後の再計算を通知ルールIssueで確定・検証する。LLMには日時を決めさせない。

OS通知はアイテム単位で予約する。通知の「開く」「完了」「あとで」は別操作で、「あとで」は追加入力なしに再計算・再予約する。通知権限拒否やOS制限時も保存・一覧閲覧を継続する。予約識別子とDBの整合、再起動後の再調整はローカル通知Issueで扱う。

## 将来の境界

- AWS Serverless: Phase 3で認証・同期が必要になった時に、保存ポートの外側へAPI Gateway / Lambda / DynamoDB / Cognitoを追加する。EventBridge / Scheduler、CloudWatch、APNs / FCMの採用と端末通知との責務分担はそのIssueで決める。Phase 1にはAWS認証や常時通信を入れない。
- OpenAI API: Phase 2で分類ポートの別実装として追加する候補。返すのは `category`、`subcategory`、`estimated_duration`、`estimated_effort`、`planning_needed`、`preferred_context` 等の属性。将来のAPI呼び出しは秘密鍵を端末に埋め込まずサーバー側に置く。AI不通時はローカル分類へ戻す。
- スマートスケジューリング: Phase 3候補。利用傾向を特徴量としてルールへ渡し、最終日時の決定権はアプリ側に残す。
